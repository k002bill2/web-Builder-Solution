# ADR-003 — 기능·솔루션 우선, 목업은 구조·위계 기준으로만

- 상태: **승인** (영환님, 2026-09-25 Slack: "목업 이미지에 모든걸 맞추지 말고 기능과 솔루션을 충분히 고려하고 디자인을 맞추는 방식으로 진행해")
- 작성: Jarvis
- 대체: ADR-001의 "목업 그대로 구현" 원칙, CLAUDE.md 규칙 3의 "레이아웃·간격·타이포·색을 충실히 옮긴다"

## 결정
구현 판단의 우선순위를 다음 순서로 둔다.

1. **기능·사용자 흐름** — PRD 요구사항(FR)과 실제 사용 시나리오가 동작하는가
2. **사용성** — 실제 데이터(긴 이름·빈 값·많은 항목), 빈/로딩/오류 상태, 접근성(키보드·포커스·대비), 반응형, 성능 예산
3. **디자인 시스템 일관성** — 토큰·DS 컴포넌트·간격 체계를 화면 간에 같게 쓴다
4. **목업** — 화면 구조, 정보 위계, 톤을 맞추는 기준. **px 단위 값은 기준이 아니다**

## 적용 규칙
- 목업과 달라도 되는 경우: 1~3을 위해 필요할 때. 차이는 PROGRESS/REPORT에 한 줄 사유로 남긴다.
- 목업에 없는 상태·화면(빈 결과, 오류, 로딩, 긴 텍스트, 권한 없음 등)은 구현 전에 정의한다.
- 새 흐름·상태 설계가 필요한 화면(1a-03 비교 보드 이후: 프로필·3안 생성·편집기·발행)은 **Designer가 구조·상태·수용 기준을 먼저** 만들고 Developer가 구현한다. 목업은 Designer의 입력 자료다.
- 유지되는 제약: 토큰만 사용(하드코딩 금지), ADR-002 브랜드 분리, 권리 경계, TDD, 검증 4종.

## QA 판정 기준 변경
- 시각 검증은 **px 대조를 하지 않는다.** 위계·정렬·일관성·가독성·반응형을 본다.
- 결함은 기능·사용성·접근성·일관성 문제만 센다. 목업과의 미세한 px 차이는 결함이 아니다.
- 증거용 캡처는 화면(뷰포트) 단위로 남긴다.
