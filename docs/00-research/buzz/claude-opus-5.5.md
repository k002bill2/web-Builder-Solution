## 0. 결론

1. **GDWEB 분류 체계는 "무드·콘텐츠 축"만 있고 "구조 축"은 없다.** [사실] GDWEB 필터는 업종 36·타겟층 11·표현방법 16·디자인컨셉 22·주색상 13·등급(GOOD/BEST)로 구성된다. 섹션 유형·그리드·타입 스케일·모션처럼 홈페이지를 *조립*하는 데 필요한 축은 없다. → 조립형 솔루션의 핵심 자산인 **구조 축 분류 체계와 섹션 라이브러리는 우리가 직접 정의하고 직접 만들어야 한다.**
2. **패턴은 2층 분류 + 3층 토큰으로 체계화한다.**
   - 선택층(사용자가 고르는 것): 업종 → 목적 → 무드
   - 조립층(엔진이 고르는 것): 섹션 유형·변형 → 그리드 → 타이포 스케일 → 컬러 역할 → 모션 레벨
   - 토큰은 W3C DTCG 2025.10 JSON 형식을 따르고, primitive → semantic → component 3층으로 둔다. "테마 = semantic 토큰 세트 하나"로 정의한다.
3. **디자인 선택 UX는 "업종 프리셋 → 무드 카드 → 3안 비교" 3단계를 권장한다.** 스타일 퀴즈는 MVP에서 제외하고 무드 카드 8장으로 대체한다. 모든 미리보기는 GDWEB 썸네일이 아니라 **우리 섹션 라이브러리로 렌더한 자체 프리뷰**로, 사용자 브랜드명을 넣어 보여준다.
4. **패턴 수집은 MVP에서 "수동 큐레이션"만 한다. GDWEB 자동 수집은 하지 않는다.** [사실] robots.txt가 `User-agent: *` / `Disallow: /`이고, 이용약관 제13조 3항은 허락 없는 사용·인용을 금지한다. [추정] 작품별 태그 할당 데이터와 스크린샷을 대량으로 수집하면 저작권법상 DB제작자 권리 침해와 부정경쟁방지법 (파)목 성과도용 주장이 나올 수 있다. 같은 분쟁에서 형사는 무죄였지만 민사에서는 성과도용이 인정된 전례가 있다(2절 D-2).
5. **생성 엔진은 "규칙 기반 조립 + LLM은 스키마 채우기만"으로 한다.** LLM이 HTML·CSS를 자유 생성하는 방식은 MVP에서 제외한다(품질 편차, 특정 사이트 모사 위험, 검증 불가). 에디터는 섹션 단위 JSON 모델과 맞는 **Puck(MIT)** 을 1순위, GrapesJS(BSD-3)를 대안으로 둔다. 발행물은 정적 사이트로 내보내 CDN에 호스팅한다.

## 2. C. 디자인 선택 기능·패턴화 방법론

### C-1. 패턴 분류 체계 (2층)

GDWEB 축을 **라벨 어휘 참고용**으로만 쓰고(일반명사라 문제없음 [추정]), 조립에 필요한 구조 축을 새로 정의한다. **GDWEB의 작품별 태그 할당 데이터는 가져오지 않는다.**

#### (1) 선택층 — 사용자가 고르는 축

| 축 | 값 설계 | GDWEB 대응 |
|---|---|---|
| 업종 | MVP 10종 — 6-1 합의 2의 목록이 정본 | 업종 36 → 병합 |
| 목적 | 문의 유도 / 예약 / 브랜드 인지 / 제품·서비스 소개 / 채용 / 정보 제공 | 없음 (신규) |
| 무드 | 아래 8개 무드 (디자인컨셉 22개를 압축) | 디자인컨셉 22 |
| 타겟 | 선택 입력(옵션). 카피 톤과 가독성 기준에만 반영 | 타겟층 11 |

**무드 8종 — GDWEB 디자인컨셉 22개 매핑 [추정, 큐레이션 때 검증]**

| 무드 ID | 이름 | 흡수하는 GDWEB 컨셉 | 기본 성향 |
|---|---|---|---|
| `trust` | 신뢰·정돈 | 신뢰적인, 안정적, 깔끔한, 심플한 | 저채도 블루·그레이, 넓은 여백, 모션 L1 |
| `premium` | 고급·미니멀 | 고급스러운, 모던한, 클래식한 | 블랙·아이보리, 세리프/명조 헤드라인, 큰 타이포 |
| `tech` | 첨단·테크 | 첨단적인, 신비적인 | 다크 서피스, 네온 액센트, 모션 L2 |

| `playful` | 발랄·친근 | 귀여운, 재미있는 | 고채도 파스텔, 일러스트, 큰 라운드 |
| `bold` | 강렬·역동 | 강렬한, 역동적인, 화려한 | 고대비, 대형 타이포, 모션 L2~L3 |

| `editorial` | 실험·에디토리얼 | 실험적인, 독특한 레이아웃, 복고적인, 한국적·동양적인 | 비대칭 그리드, 에디토리얼 타이포 |

- "한국적·동양적인"과 "복고적인"은 모티프 성격이 강하다. MVP에서는 `editorial`에 넣고, 수요를 보고 별도 무드로 분리한다.

**② 레이아웃 그리드** — 12열 기준 + 컨테이너 폭 3단(narrow 720 / default 1200 / wide 1440 px) + 분할 비율 프리셋(1:1, 5:7, 4:8, 7:5) + 풀블리드 허용 여부 + 모바일 1열 붕괴 규칙.

**③ 타이포그래피**
- 타입 스케일 비율 4종: 1.2 / 1.25 / 1.333 / 1.5 (무드별 기본값 존재)
- 헤드라인 계열: 고딕 / 명조·세리프 / 디스플레이
- 본문은 고딕 고정
- 폰트는 **상업·웹 임베딩 허용 라이선스만** 쓴다(예: Pretendard, Noto Sans/Serif KR — OFL [사실: 일반 지식, 법무 확인 필요])

**④ 컬러 무드** — GDWEB 주색상 13개는 hue 버킷일 뿐이라 조립에 바로 쓸 수 없다. 우리 쪽은 **역할 기반 팔레트**로 정의한다: `primary / accent / neutral(0~900) / surface / on-surface`. 조합 시 WCAG 2.x AA 대비(본문 4.5:1, 큰 글자 3:1)를 자동 검사한다.

**⑤ 모션 레벨**

| 레벨 | 허용 범위 |
|---|---|
| L0 | 없음 |
| L1 | 페이드·호버 |
| L2 | 스크롤 리빌, 약한 패럴랙스, 숫자 카운터 |
| L3 | 핀 고정 스크롤, 가로 스크롤, 풀스크린 전환 |

- `prefers-reduced-motion`이면 L0으로 강제한다.
- MVP는 L0~L2만 지원한다.

### C-2. 디자인 토큰 구조

- 형식: **W3C DTCG Design Tokens Format 2025.10** (2025-10-28 첫 안정판) [사실: https://www.w3.org/community/design-tokens/2025/10/28/design-tokens-specification-reaches-first-stable-version ]
  - [사실, 같은 출처] Figma·Penpot·Style Dictionary·Tokens Studio 등이 이 형식을 지원한다고 발표됐다.
- 3층 구조:
  1. **primitive**: 원시값(`color.blue.600`, `size.16`, `font.family.pretendard`)
  2. **semantic**: 역할(`color.primary`, `color.surface.alt`, `type.heading.1`, `radius.card`, `motion.level`)
  3. **component**: 섹션 전용(`hero.title.size`, `cta-band.bg`)
  - 규칙: 섹션 코드는 semantic·component 토큰만 참조한다. primitive 직접 참조와 하드코딩 값은 **lint 에러**로 처리한다.
- **테마 = semantic 토큰 세트 1개.** 무드 8종 × 밀도 2단(여유/촘촘) = 기본 테마 16종으로 시작한다.

```json
{
  "color": {
    "primary":   { "$type": "color", "$value": "{color.blue.600}" },
    "surface":   { "$type": "color", "$value": "{color.neutral.0}" },
    "on-surface":{ "$type": "color", "$value": "{color.neutral.900}" }
  },
  "type": {
    "scale-ratio": { "$type": "number", "$value": 1.25 },
    "heading-family": { "$type": "fontFamily", "$value": "{font.family.pretendard}" }
  },
  "motion": { "level": { "$type": "number", "$value": 1 } }
}
```

### C-3. 섹션 컴포넌트 계약

섹션마다 다음 계약(스키마)을 둔다. 에디터·생성 엔진·렌더러가 이 계약 하나를 함께 쓴다.

- `type`, `variant`
- `slots`: 제목·본문·이미지·버튼 등. 타입·글자수 상한·필수 여부 포함
- `constraints`: 허용 무드, 허용 모션 레벨, 최소 대비, 모바일 동작
- `tokens`: 참조하는 semantic·component 토큰 목록
- `a11y`: 대체텍스트 필수 여부, 헤딩 레벨 규칙
- `provenance`: 누가 언제 만들었는지, 참고한 추상 패턴 ID. **특정 사이트 URL이나 캡처는 넣지 않는다.** 관찰 출처 URL은 접근 통제된 조사 원장에만 둔다(TRD-D-04).

### C-4. 테마·섹션 조합 규칙 (조립 엔진 + lint)

1. 페이지 = `header` 1개 + 본문 섹션 5~9개 + `footer` 1개
2. `hero`는 첫 본문 섹션에만, 정확히 1개
3. 목적별 필수 섹션:
   - 문의 유도 → `cta-band` 또는 `contact-location` 중 1개 이상, 페이지 후반 1/3에 배치
   - 예약 → `contact-location`(예약 링크 변형) 필수
4. 인접 섹션은 배경 톤(surface ↔ surface.alt ↔ primary)이 같지 않아야 한다(시각 리듬). 풀블리드 섹션은 연속 2개까지만.
5. 페이지 전체의 타입 스케일·헤드라인 계열·모서리 반경은 테마 값 1개로 고정한다. 섹션별로 덮어쓰지 않는다.
6. 모션 예산: L2 섹션은 페이지당 3개 이하, L3는 1개 이하(MVP에서는 0).
7. 대비 검사를 통과하지 못한 조합은 발행을 차단하고 대체 토큰을 제안한다.
8. 업종 프리셋 = 추천 섹션 순서 템플릿. 예) 병·의원: hero(분할) → intro → service-list → team → stats → news → contact-location
   - [추정] GDWEB 상세 페이지의 "유사 업종/유사 컨셉" 추천 구조가 업종·무드 축 추천이 성립한다는 근거다. Fable 관찰과 같은 판단이다.

### C-5. 디자인 선택 UX

| 방식 | 장점 | 단점 | MVP 판단 |
|---|---|---|---|
| 업종 프리셋 | 가장 빠름, 섹션 구성까지 한 번에 결정 | 결과가 비슷해질 위험 | **기본 진입** |
| 무드 카드(무드보드) | 시각적으로 직관적, 선택 1~2회 | 카드 품질에 전적으로 의존 | **채택 (8장)** |
| 스타일 퀴즈(A/B 쌍비교 5~7문항) | 취향을 세밀하게 추정 | 이탈 증가, 문항 설계와 검증 비용 | 2차 |
| 레퍼런스 URL 입력 → 무드 추정 | 사용자 친화적 | 특정 사이트 모사 요청 창구가 됨(법적 위험) | **제외** |

**권장 흐름**

1. 업종과 목적 선택. 브랜드명·로고·대표색(선택) 입력
2. 무드 카드 8장 중 1장 선택. 카드는 **사용자 브랜드명이 들어간 자체 렌더 hero 미리보기**다.
3. 시스템이 3안을 제안한다(같은 무드 안에서 hero 변형·그리드·타입 스케일을 다르게). 나란히 비교 후 1안 선택
4. 에디터에서 섹션 추가·교체·순서 변경. 전역 조정 슬라이더 3개: 밀도, 대비, 모션
5. 발행 전 lint 결과(대비·필수 섹션·대체텍스트)를 보여준다.

- 무드 카드·예시 이미지에 **GDWEB 썸네일이나 선정작 캡처를 쓰지 않는다.** 전부 우리 섹션 라이브러리와 라이선스를 확보한 스톡으로 만든다.

1. GDWEB의 **작품별 분류 태그 + 캡처 + 심사 등급** 묶음은 20년간(2005~) 심사 투자로 만든 DB·성과로 인정될 가능성이 높다. 이를 대량 수집해 경쟁 서비스(디자인 탐색·추천)에 쓰면 (파)목 요건인 "경쟁관계·시장 대체"를 충족할 여지가 있다.

## 5. PRD / TRD 요구사항 후보

**PRD (C. 디자인 선택·패턴화)**
1. PRD-C-01 사용자는 업종(MVP 8~10종)과 목적(6종)을 고르고, 브랜드명·로고·대표색을 입력한다.
2. PRD-C-02 사용자는 무드 카드 8장 중 1장을 고른다. 카드는 사용자 브랜드명이 들어간 자체 렌더 미리보기다.
3. PRD-C-03 시스템은 선택값으로 서로 다른 3안(hero 변형·그리드·타입 스케일 차이)을 제안하고, 사용자는 나란히 비교해 1안을 고른다.
4. PRD-C-04 에디터는 섹션 추가·삭제·순서 변경·변형 교체·슬롯 편집을 지원한다. 픽셀 자유 배치와 임의 CSS는 지원하지 않는다(MVP).
5. PRD-C-05 전역 조정 슬라이더 3개(밀도·대비·모션)를 제공한다. 테마 토큰 범위 안에서만 움직인다.
6. PRD-C-06 MVP 섹션 라이브러리는 16개 유형 × 2~4개 변형이며, 모든 변형은 모바일 1열 붕괴 규칙을 갖는다.
7. PRD-C-07 업종 프리셋마다 추천 섹션 순서 템플릿을 제공한다.
8. PRD-C-08 발행 전에 lint 결과(대비 AA·필수 섹션·대체텍스트·모션 예산)를 보여주고, 위반 항목은 발행을 막는다.
9. PRD-C-09 레퍼런스 URL을 넣어 "비슷하게 만들기" 기능은 제공하지 않는다.
10. PRD-C-10 섹션·테마의 내부 품질 루브릭은 비주얼·정보구성·사용성·기술요소·아이덴티티 5개 영역으로 평가한다(GDWEB 심사 항목을 틀로 참고).

**TRD (D. 기술·리스크)**
1. TRD-D-01 디자인 토큰은 W3C DTCG 2025.10 JSON으로 저장하고 primitive/semantic/component 3층으로 둔다. 섹션 코드의 primitive 직접 참조와 하드코딩 값은 lint 에러다.
2. TRD-D-02 패턴 수집 파이프라인은 GDWEB 등 제3자 갤러리를 자동 수집하지 않는다. 외부 사이트 요청은 robots.txt와 약관을 확인한 뒤에만 한다. 브라우저 UA 위장은 금지한다.
3. TRD-D-03 섹션 계약 스키마(type·variant·slots·constraints·tokens·a11y·provenance)를 에디터·생성 엔진·렌더러가 함께 쓰는 단일 소스로 둔다.
4. TRD-D-04 provenance는 이중 구조로 둔다(GPT-Sol 검토 `gpt-sol.md` TRD-E-14 수용). 생산 객체(섹션·테마)에는 제작자·일시·추상 패턴 ID만 저장하고 외부 URL은 넣지 않는다. 별도의 **접근 통제된 조사 원장**에 관찰 URL·관찰일·약관/robots 확인 결과·추상화 메모·승인자를 보관해 권리 검토·삭제 요청에 대응한다. 외부 이미지·HTML·캡처는 어느 저장소에도 보관하지 않는다.
5. TRD-D-05 생성 엔진 = 규칙 기반 조립기(결정적, 변형 선택·순위 포함) + LLM은 빈 슬롯 카피 초안만. LLM 출력은 JSON 스키마 검증을 통과해야 반영하고, 실패 시 정적 플레이스홀더로 폴백한다. LLM 자유 HTML 생성은 사용하지 않는다.
6. TRD-D-06 조합 규칙(C-4 1~7)을 코드 검증기로 구현하고 단위 테스트한다.
7. TRD-D-07 에디터는 Puck(MIT)으로 PoC하고, 섹션 계약 → Puck config 변환 계층을 둬서 에디터를 교체할 수 있게 한다.
8. TRD-D-08 발행은 정적 HTML 내보내기 + CDN + 커스텀 도메인 TLS 자동화. 호스팅 사업자는 비용·레이턴시 비교 후 결정한다.
9. TRD-D-09 `prefers-reduced-motion`을 감지하면 모션 레벨 L0으로 강제한다. MVP는 L0~L2만 지원한다.
10. TRD-D-10 번들 폰트·스톡 이미지는 허용 목록 방식이며, 에셋마다 라이선스 메타데이터를 저장한다.
11. TRD-D-11 신규 섹션을 등록할 때 내부 유사도 검사(레이아웃 구조 + 색상 + 카피)를 실행하고 결과를 기록한다.

## 6. Fable 산출물과 교차 확인할 쟁점

1. **MVP 범위** — 이 문서의 가정:
   - 업종 8~10종, 무드 8종, 섹션 16종, 스타일 퀴즈 제외
   - GDWEB식 "선정작 갤러리 탐색"은 우리 제품에 넣지 않고, 우리 섹션·테마 갤러리로 대체
   - Fable의 서비스 흐름(탐색→선택→편집→발행)에서 "탐색" 대상이 무엇인지 맞춰야 한다.
2. **패턴 수집 방식** — 이 문서의 입장:
   - 수동 큐레이션만 하고 GDWEB 자동 수집은 금지
   - 제휴 문의는 병행
   - Fable 쪽에 "GDWEB 데이터 활용" 전제가 있으면 여기서 조정한다.

### 6-1. 교차 코멘트 결과 — 합의안 (2026-09-25, Fable `claude-fable.md` E절과 대응)

- 쟁점 1·2 해소: "탐색" 대상은 우리 프리셋·섹션·테마 갤러리. 양측 모두 GDWEB 데이터 활용 전제 없음.
- 합의 1 — 목적 축: 이 문서의 6종(문의 유도/예약/브랜드 인지/제품·서비스 소개/채용/정보 제공)을 정본으로 한다. 프리셋은 업종×목적 전조합(최대 60)이 아니라 업종별 대표 목적 2~3개만 사전 정의하고 나머지는 섹션 세트 규칙으로 파생한다.
- 합의 2 — 업종 10종: 병·의원 / 법률·세무·전문직 / 교육·학원 / 음식·카페·식품 / 뷰티·살롱 / 건축·인테리어·부동산 / 제조·B2B 기업소개 / IT·스타트업 / 공공·단체·협회 / 문화·예술·행사·프로모션.
  - "포트폴리오·개인"은 업종에서 빼되, 목적을 7종으로 늘리지 않는다. 목적 "제품·서비스 소개" 아래 `showcase` 중심 섹션 세트(작품·경력 소개)로 파생한다.
- 합의 3 — LLM: 빈 슬롯 카피 초안만. 변형 순위는 규칙 기반. 실패 시 정적 플레이스홀더 폴백(D-3, TRD-D-05 반영).
- 합의 4 — GDWEB "표현방법"은 사용자 선택 축이 아니다. `hero`(및 `showcase`·`intro`) 변형을 **레이아웃 × 미디어 슬롯** 2차원으로 분리한다.
  - 레이아웃: 풀블리드 / 좌우 분할 / 타이포 중심 / 슬라이드
  - 미디어 슬롯 속성: 사진 / 영상 / 일러스트 / 3D 렌더 이미지(정적) / 없음(타이포만)
  - 실시간 3D(WebGL)는 모션 L3와 함께 MVP 제외.
- 합의 5 — 섹션 수량: 16유형 × 2~4변형을 정본으로 한다. 프리셋 기본 본문 섹션은 5~7개, 편집 시 상한 9개.

### 6-2. GPT-Sol 교차검토 반영 (`gpt-sol.md`)

- 수용: provenance 이중 구조 → TRD-D-04, C-3 수정.
- 수용: LLM 카피는 핵심 경로 밖 선택형 플래그. 조립·발행은 LLM 없이 결정적으로 완주한다(합의 3과 양립).
- 범위: GPT-Sol의 베타 범위(5업종 × 3목적 × 4무드, 12유형 × 2변형)는 이 문서 MVP 라이브러리(10업종·6목적·8무드·16유형 × 2~4변형)의 **부분집합**이라 충돌하지 않는다. 베타 → MVP 확장 순서로 둘지는 PRD에서 요청자가 결정한다.
