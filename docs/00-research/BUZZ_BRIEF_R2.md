## 1. 왜 다시 검토하나 (영환님 문제 제기)
영환님 목표는 **이 프로세스 안에서 "최종 시안"까지 만드는 것**이다 — 벤치마크 → 비교 → 선택 → 생성의 끝에 **실제로 보이는 완성 시안(이미지 포함)과 동작하는 코드**가 나와야 한다.
현재 결과물은 그 끝에 닿지 않는다. 영환님 질문: "지금은 시안까지 **흉내만 내는** 기획안·솔루션인가?"

### 현재 상태 (사실 — 저장소 근거)
- 구현됨: 레퍼런스 카탈로그·상세·비교 보드 → 디자인 프로필(버전) → 3안 구조안(`/profile`) → 편집기 `/studio/:projectId`(섹션 순서·추가·삭제·변형 교체·슬롯 글자·자동 저장). 편집 결과 = **PageDoc JSON 1건**(`app/src/engine/contracts/pageDoc.ts`).
- 캔버스 = **구조 미리보기(와이어프레임 블록 + 실제 문구)**. SPEC 5.7 캡션: "실제 페이지는 생성기 연결 후(M2) 만들어집니다."
- 내보내기 = a4에서도 "코드 생성기 연결 후(M2) 내보낼 수 있습니다" 안내만(SPEC `docs/design/2a-05/SPEC.md` E-S27, EQ-1 A — 가짜 zip 금지).
- 계획상 실제 결과물: **M2** 섹션 킷(12유형×2변형)·토큰→Tailwind·codegen / **M4** zip·정적 내보내기 / **M5** 발행 (`docs/04-plan/DEVELOPMENT_PLAN.md` 1절·M2 표).
- **순서 이탈**: 계획은 M2(생성기) → M3(편집)인데, 실제 진행은 편집기(2a-05 ≈ M3)를 생성기보다 먼저 만들었다. 섹션의 실제 렌더 컴포넌트가 아직 없다.
- **이미지 제작은 어느 단계에도 없다.** PRD 원칙 2 "자체 제작 섹션과 사용 허가된 에셋만", 이미지 슬롯 = 자체 플레이스홀더(대각 줄무늬) 또는 사용자 로컬 업로드(SPEC 5.9·EQ-3). 생성형 이미지 요구사항 0건. 카피는 FR-GEN-07 LLM 초안(P2, 빈 슬롯만)뿐.
- 제약(유지): ADR-004 번들 예산 첫 화면 100KB gzip, 공용 컴포넌트 hex 0·토큰만, 외부 사이트 이미지·문구 금지, GDWEB 읽기 전용(robots `Disallow: /`).

## 2. 담당 분장 (중복 금지)

**Claude-Fable — A. 제품 정의·파이프라인·단계 재배열**
1. "최종 시안"의 정의를 제안하라: (a) 고해상도 시각 시안 이미지(PNG/PDF, 데스크톱·모바일) (b) 실제 렌더된 반응형 페이지(브라우저 미리보기) (c) 내려받는 코드(React+Tailwind zip / 정적 HTML) — 각각 사용자 가치·필요 입력·MVP 포함 여부.
2. 현재 산출물(PageDoc + 구조 미리보기)에서 1의 결과물까지 **끝까지 이어지는 파이프라인**을 단계별로 그려라(입력 → 변환 → 산출물, 누가/무엇이 만든다).
3. 현 계획(M2~M5)과의 **갭 목록**과, "편집기 먼저" 순서 이탈을 바로잡는 **재배열안**(예: 섹션 킷 렌더러를 캔버스에 먼저 연결) — 이미 만든 편집기·엔진 중 재사용/폐기 대상 구분.
4. 에이전시 "10분 안에 비교 가능한 시안 3안"(PRD 48행) 기준으로 가장 짧은 수직 슬라이스 1개 제안.

**Claude-Opus 5.5 — B. 이미지 제작 + 코드 생성 기술·리스크**
1. **렌더러**: PageDoc → 실제 섹션 컴포넌트 렌더. 편집기 캔버스에 쓰는 방식(같은 React 트리 vs `iframe` 샌드박스 vs 서버 렌더 스크린샷) 비교 — ADR-004 번들 예산(섹션 킷을 별도 청크/iframe으로 격리)과 충돌 여부.
2. **codegen·내보내기**: React+Tailwind 프로젝트 파일 생성, 정적 HTML 빌드, zip — 브라우저 단독(클라이언트) vs 백엔드 워커(현재 백엔드 미정) 선택지와 MVP 권장.
3. **이미지 제작**: 이미지 슬롯을 채우는 방법 선택지 — 생성형 이미지 모델 API, 스톡 라이선스 API, 사용자 업로드, 프로필 토큰 기반 추상 그래픽(SVG/패턴) 자체 생성. 각각 권리·라이선스(PRD 원칙 2 "사용 허가된 에셋만"과의 충돌·필요한 정책 변경), 비용, 품질, 보안(키 보관·서버 경유), 저장·최적화(AVIF/WebP·srcset, TRD 277행).
4. **시안 이미지 산출**: 렌더된 페이지를 PNG/PDF 시안으로 뽑는 방법(헤드리스 브라우저 스크린샷 등)과 실행 위치.
5. 위 1~4에 필요한 **백엔드·인프라 최소 구성**과 보안 검토 항목.

**공동(두 에이전트 각자 관점) — C. 레퍼런스 데이터 확보 전략 (영환님 추가 질문, 2026-09-28)**
- 현재 사실: GDWEB 크롤링 0건. 카탈로그 = 손으로 만든 픽스처 6건(`app/src/fixtures/references.ts`, `internal` 4 · `licensed` 2, 가상 사이트). PRD 원칙 3·5(39·41행)가 GDWEB 이미지·태그 수집과 외부 URL 스크린샷 수집을 MVP에서 제외했고, 근거는 robots `Disallow: /`·이용약관 제13조(`claude-opus-5.5.md` 19·70~81·243행). PRD 190행이 "internal 위주라 벤치마크 가치가 약해 보임"을 위험으로 이미 적었다.
- 질문: "많은 사이트의 디자인 데이터를 불러오는" 제품 가치를 **합법적으로** 얻는 경로를 비교하라 — (1) GDWEB 운영사 제휴·데이터 라이선스 (2) 에이전시·디자이너 opt-in 제출(자기 작품) (3) robots·약관이 허용하는 공개 사이트를 사람이 보고 **추상 패턴 태그만** 기록(이미지·문구 저장 0) (4) 우리 섹션 킷으로 레퍼런스 사이트를 대량 자체 생성(`internal`) (5) 사용자가 자기 프로젝트에만 비공개로 올리는 참고 캡처. 각 경로의 규모(몇 건/주), 비용, 법적 위험, 제품 가치, 필요한 도구·파이프라인.

## 3. 공통 규칙
- 답 형식: **결론 → 근거(저장소 파일·행 / 외부 URL) → 사실·추정·확인 필요 구분 → 요구사항·결정 후보(번호 목록, 영환님 결정이 필요한 것은 ★추천 표시)**.
- 저장소는 **읽기 전용**. 코드·SPEC·설계 문서를 수정하지 않는다. 파일 쓰기는 자기 산출물 파일 1개에만.
- 외부 사실(모델·API·가격·라이선스)은 출처 URL 필수, 기준 날짜 표기.
- 특정 선정작·타 사이트 디자인·이미지를 복제하는 방안은 제안하지 않는다. GDWEB은 읽기 전용 관찰만(로그인·스크랩·심사등록·대량 크롤링 금지), 이번 검토는 GDWEB 추가 관찰이 필요 없다.
- 외부 발송·게시·Git 원격 쓰기 금지.
- 스레드 답글 = 핵심 요약 1건(결정 후보 포함) + 산출물 파일 경로. 서로의 결론이 충돌하면(예: 렌더러 위치, 이미지 정책) 같은 스레드에서 1회 교차 코멘트로 정리.
