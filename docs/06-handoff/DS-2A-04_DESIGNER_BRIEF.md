## 1. 과제
1. **범위 정의**: 2a-04에 들어가는 것 / 2a-05(편집기)로 넘기는 것 / M2 생성기(섹션 킷·composer·codegen) 없이는 만들 수 없는 것을 표로 나눈다. 현재 백엔드 미정·생성기 없음(메모리 저장소 + fixtures)이라는 전제에서 **이번 프런트 단계에 실제로 구현 가능한 최소 범위**를 제안한다.
2. **사용자 흐름·상태**: 비교 보드 확정(`/profile/:profileId` 진입) → 프로필 검토 → 전역 조정 → 3안 생성 → 안 비교·선택 → (편집기 진입은 경계만). 각 화면 상태: 로딩·빈·오류·생성 중·생성 실패·부분 실패·버전 있음/없음·대비 미달 보정 제안·범위 밖 값.
3. **프로필 화면 구조**: DesignProfile 필드(FR-PRF-01) 중 무엇을 어떻게 보여 줄지, 출처 레퍼런스 표시(권리 경계 PRD 4절), 역할 팔레트·대비 표시(FR-PRF-02), 버전 목록·비교·되돌리기(FR-PRF-03), 전역 조정 밀도·대비·모션(FR-PRF-04 — **슬라이더는 키보드·값 텍스트 필요**, SPEC 6.5 쟁점).
4. **3안 생성·비교 구조**: 3안의 차이 축(FR-GEN-04), 생성 로그 요약 3줄(FR-GEN-05), 조합 lint 경고(FR-GEN-06), 결정성 표시(FR-GEN-03, 같은 입력 → 같은 결과). 미리보기 썸네일은 자체 렌더 플레이스홀더(외부 캡처 금지).
5. **반응형·접근성**: 1920·1280·1024·768·390. 비교 보드와 같은 브레이크포인트·패턴 재사용. 키보드 흐름, 라이브 영역(생성 진행·완료·실패), 상태를 색 하나로만 알리지 않기(C-12), 대비는 v2 SPEC 3절 방법으로 계산.
6. **데이터 계약 초안**: 화면이 필요로 하는 읽기·쓰기(프로필 조회, 버전 목록, 조정 저장, 생성 요청·상태·결과)를 **저장소 인터페이스**(현행 `*Repository` 패턴) 수준으로. 백엔드 선택은 하지 않는다 — 결정이 필요하면 7번 설계 질문으로.
7. **번들 영향**: `/profile` 라우트 새 청크 예산(ADR-004: 첫 화면 ≤ 100KB, 진입 직후 ≤ 125KB). 공통 청크 증가 금지, 파일화 아이콘 5개 규칙, `import type` 규칙을 설계에 반영.
8. **단계 구현 계획**: Developer 작업 단위(예: 2a-04a 프로필 조회·버전, 2a-04b 전역 조정, 2a-04c 3안 생성·비교)와 단계별 수용 기준(AC ID `P-AC-NN`), 깨질 기존 테스트 예상(자리표시 라우트 등).
9. **설계 질문**: 영환님 결정이 필요한 것만, 번호·추천안·트레이드오프 포함. 특히 "생성기 없이 3안을 어떻게 보여 줄지"(가짜 생성 금지 여부·fixtures 기반 결정적 목업 생성 등).
