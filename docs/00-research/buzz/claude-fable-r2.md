## 0. 결론 (요약)

1. **"최종 시안"의 정본은 (b) 실제 렌더된 반응형 페이지다.** (a) 시안 이미지와 (c) 코드는 (b)에서 파생된다. 셋 다 같은 `PageDoc` 리비전·라이브러리 버전·생성기 버전을 가리켜야 하고(FR-GEN-03 결정성), 그래서 "시안 = 파일"이 아니라 **"시안 = (문서, 버전) 참조 + 파생물 3종"**으로 정의한다.
2. **지금 결과물은 "흉내"가 아니라 "표면이 없는 미완"이다.** 구조(섹션·변형·슬롯·톤·모션·게이트·스냅샷·멱등 내보내기 잡)는 실제 계약대로 동작하고 스스로 미완임을 정직하게 표시한다 — 캔버스 캡션(`app/src/components/studio/StructureCanvas.tsx:12`), 내보내기가 `GENERATOR_UNAVAILABLE`로 끝나는 판정 순서(SPEC 8.3.2 6단계). 빠진 것은 데이터가 아니라 **"PageDoc → DOM" 변환기 하나**와, 그것을 캔버스·캡처·codegen이 **공유**하는 구조다.
3. **갭은 9개(A-3)이고, 그중 "이미지 제작"과 "시안 캡처"는 현 계획 M2~M5 어디에도 없다.** M4 4.1의 "3뷰포트 스크린샷"은 QA 게이트용이지 사용자에게 주는 시안이 아니다.
4. **재배열: M2를 셋으로 쪼개고 M2a(렌더 슬라이스)를 지금 바로 앞에 둔다.** 편집기·엔진은 전부 재사용한다. 폐기 대상은 `canvasLayouts`의 모양표와 줄무늬 이미지 자리뿐이며, 그것도 "렌더러가 없는 변형의 폴백"으로 실렌더 완료 때까지 남긴다. "편집기 먼저" 이탈은 되돌릴 비용이 거의 없다 — 편집기는 렌더러를 몰라도 되게 지어졌다.
5. **가장 짧은 수직 슬라이스(VS-1): 변형 4개만 실제로 렌더해서 "B안 선택 → 진짜 페이지 → 데스크톱/모바일 → PNG 1장 + 정적 HTML 1개 내려받기"를 브라우저 단독으로 끝낸다.** 백엔드 0, 새 라우트 0. React 프로젝트 zip은 빌드 검증이 필요하므로 워커가 생기는 M4로 남긴다.
6. **이미지(MVP 시안용): 프로필 토큰으로 자체 생성한 그래픽 + 사용자 업로드로 충분하다.** 생성형·스톡은 권리·비용·보안이 붙는 P2 옵션이다(선택지 비교는 Opus B-3, 나는 제품 가치 관점만 A-1에 적었다).
7. **C. 데이터 확보 결론은 C-0에** — 규모는 (4) 자체 생성만이 주 100건 이상이지만 "남의 사이트를 본다"는 벤치마크 가치가 없고, 그 가치는 (2) opt-in 제출과 라이선스가 명시된 외부 데이터셋에서만 나온다. 추천은 **"레퍼런스 = 검증된 조합"으로 제품 정의를 바꾸고, internal 대량 + licensed 소수 고품질의 이중 카탈로그**.

### 정의 제안 (PRD 용어)

> **최종 시안** = 특정 `PageDoc` 리비전 *r*을 라이브러리 버전 *L*·생성기 버전 *G*로 렌더한 결과의 묶음 `{ preview(b), capture(a), export(c) }`. 세 파생물은 같은 `(r, L, G)`와 같은 `doc_hash`를 가리키고, 어느 하나만 따로 만들어지지 않는다.

- 이 정의가 주는 것: "PNG는 예쁜데 코드는 다르다"(PRD 2.2 "시안과 개발 결과 차이")를 구조적으로 막는다. TRD 4.4 160행 "대시보드 미리보기와 코드 생성기가 **같은 컴포넌트**를 쓴다"가 이미 이 뜻이다 — 계획엔 있고 코드엔 없다.
- **완성도 사다리(시안 등급)** — 어디까지를 "시안"이라 부를지 합의용:

| 등급 | 내용 | 지금 |
|---|---|---|
| F0 | 구조 와이어프레임 + 실제 문구 | **여기** (`StructureCanvas`) |
| F1 | 실제 섹션 컴포넌트 렌더 + 토큰 색·타이포 + 이미지는 자체 플레이스홀더 | VS-1 목표 |
| F2 | F1 + 자체 그래픽/사용자 이미지 + 자체 호스팅 폰트 + 모션 프리셋 | **MVP "최종 시안"** |
| F3 | F2 + 게이트 통과 + 코드(zip) + 발행 가능 | MVP 발행 조건 |

★ **MVP "최종 시안" = F2.** F1은 사용자에게 보여 줄 수 있지만 "시안"이라 부르지 않는다(캡션으로 등급 표시).

### 이미지에 대한 제품 관점 (선택지 비교는 Opus B-3)

- PRD 원칙 2(38행) "자체 제작 섹션과 사용 허가된 에셋만"은 이미지 슬롯의 **기본값이 자체 제작이어야 한다**는 뜻으로 읽는다. 지금 자체 제작은 "대각 줄무늬"(`pageDoc.ts:33-37`)뿐이다.
- 시안 단계에서 사용자가 실제로 겪는 문제는 "사진이 없다"가 아니라 **"플레이스홀더 때문에 시안이 시안처럼 안 보인다"**다. [추정] 그래서 MVP 이미지 전략의 1순위는 생성형이 아니라 **프로필 토큰(팔레트·무드)으로 결정적으로 만드는 자체 그래픽**(그라디언트·기하 패턴·타이포 카드·브랜드 이니셜)이다. 결정적이라 FR-GEN-03과 충돌하지 않고, 권리 문제가 0이고, 서버가 필요 없다.
- 2순위 사용자 업로드(이미 SPEC 5.9 A안: 브라우저 안, 5MB, JPEG/PNG/WebP). 3순위 스톡 API(라이선스 메타 필수, TR-POL-05). 4순위 생성형(P2 플래그, 의료·금융 업종 제한, 사용량 원장 FR-ORG-02). 우선순위만 여기서 정하고 각 선택지의 권리·비용·보안 비교는 Opus B-3에 맡긴다.

파이프라인의 핵심 제약 3개(제품 관점, 기술 방식은 Opus B-1·B-2):

1. **S5는 하나여야 한다.** S5'·S7·S8이 각자 그리면 "시안 ≠ 코드"가 다시 생긴다. 렌더 컴포넌트는 엔진 데이터 계약과 **분리된 레지스트리**(예: `engine/render/`)에 두어 엔진은 데이터만 유지하고(현 REPORT 표 결정 존중) 번들도 따로 나눈다.
2. **S5는 ADR-004 예산 밖에서 그려져야 한다.** 섹션 킷은 앱 DS와 다른 토큰(생성 홈페이지 예산 ≤ 90KB, TRD 277행)을 쓰므로 앱 라우트 청크에 섞이면 100/125KB를 바로 넘긴다. [추정] 별도 문서(iframe)에 킷 청크를 싣는 것이 자연스럽다 — 판단은 Opus B-1. 단, "진입 직후 자동 로드"로 분류되면 125KB 합계에 들어가므로(SPEC 10.2 S-B5 규칙) **측정 규칙을 먼저 정해야 한다** [확인 필요].
3. **S6·S7·S9의 MVP 실행 위치는 브라우저다.** 백엔드가 미정인 상태(TRD 0절·12절 3)에서 시안까지 가는 길을 백엔드에 걸면 M2가 다시 밀린다. 워커가 꼭 필요한 것은 React zip 빌드 검증(FR-PUB-02 "npm run build 성공")과 발행뿐이다.

### "편집기 먼저" 순서 이탈 평가

- [사실] 계획은 M2(생성기) → M3(편집)인데 2a-05(≈M3)를 먼저 만들었다.
- [판단] **손실은 작다.** 편집기는 렌더러에 의존하지 않도록 지어졌다: 엔진은 데이터 계약만(`sectionDefinition.ts:3`), 문서 연산은 순수 함수(`pageDoc.ts:2-3`), 화면은 `instanceId`로만 섹션을 가리킨다. 렌더러는 이 문서를 **읽기만** 하면 된다. 재작업이 생기는 곳은 한 군데 — **문제 표시(FR-EDT-05)**. 지금은 와이어프레임 블록 안에 2중 테두리로 그리는데(SPEC 5.7 B-03, `StructureCanvas.tsx` `IssueText`), 실렌더 위에서는 섹션 컴포넌트를 건드리지 않는 **오버레이 층**(`instanceId` 앵커)으로 다시 만들어야 한다.
- [판단] 얻은 것도 있다: 편집기가 먼저 있으니 렌더러를 **변형 1개씩** 붙이며 즉시 눈으로 검증할 수 있다(폴백 = 와이어프레임). 생성기를 먼저 만들었다면 24변형이 다 나올 때까지 아무도 못 봤을 것이다.

## A-4. 가장 짧은 수직 슬라이스 — VS-1 "보이는 시안 한 장"

**기준:** PRD 48행 에이전시 "10분 안에 비교 가능한 시안 3안". 10분의 대부분은 이미 있는 S0~S2(보드→프로필→3안)가 쓴다. VS-1은 그 끝에 **"보이는 것"** 하나를 붙인다.

**범위(IN)**

## A-6. 결정 후보

1. ★ **"최종 시안" 정의 = F2 등급 렌더 페이지가 정본, PNG·정적 HTML은 같은 `(r, L, G)`의 파생물.** React zip은 P0 유지하되 M4. (대안: PNG를 정본으로 두고 렌더는 나중 — 기각, "시안 ≠ 코드" 재발.)
2. ★ **M2를 M2a/M2b/M2c로 분할하고 M2a(VS-1)를 즉시 착수.** 편집기·엔진 전부 재사용, 폐기는 캔버스 모양표뿐.
3. ★ **VS-1 범위 = 변형 4개 실렌더 + PNG + 정적 HTML, 브라우저 단독.** (대안: 12유형 × 1변형 = 12개 먼저 — 2배 기간, 첫 시안이 4주로 밀림.)

## C. 데이터 확보 — 제품 가치·규모·운영 흐름 관점

외부 사실은 researcher 서브에이전트가 2026-09-28에 1차 출처(약관·라이선스·데이터셋 카드)를 직접 열어 확인한 것이다(URL은 C-4). 법·기술·자동화 관점은 Opus R2 "C. 데이터 확보"와 교차한다. GDWEB 운영사 제휴(경로 1)는 영환님 확정으로 제외.

### C-0. 결론

1. **"많은 사이트의 디자인 데이터"는 두 가지 다른 가치를 섞어 부르는 말이다.** (V1) *영감·탐색* — 남이 만든 실제 사이트를 많이 본다. (V2) *선택 근거* — 구조·토큰·태그·점수로 비교할 수 있고 그대로 생성할 수 있다. 우리 제품이 만드는 것은 V2에서만 나온다(FR-SEL-01 "레퍼런스와 같은 섹션 구성으로 생성"은 그 레퍼런스가 우리 섹션으로 조립돼 있을 때만 성립). **V1을 대량으로 주는 합법 경로는 없다** — 그 시장은 GDWEB·Awwwards·Mobbin이 약관으로 잠가 두고 직접 하고 있다(C-4). 
2. **따라서 제품 정의를 "레퍼런스 = 남의 사이트"에서 "레퍼런스 = 검증된 조합(업종×목적×무드)"으로 바꾸는 것이 첫 결정이다.** 이 바꿈 없이는 어떤 경로를 골라도 PRD 190행 위험("internal 위주라 벤치마크 가치가 약해 보임")이 그대로 남는다. 바꾸면 카탈로그의 가치 문장은 "이 업종에서 검증된 구성 N개 중 고르고, 그대로 만든다"가 된다.
3. **규모가 나오는 경로는 (4) 자체 생성뿐이고, "실제 사례"의 신뢰는 (2) opt-in 제출에서만 온다.** (3) 추상 태그 기록은 카탈로그 항목을 만들지 못하고 **변형의 근거(provenance)**를 만든다 — 사용자 눈에 보이지 않지만 TR-POL-04(근거 3개)를 채우는 유일한 경로다. (5) 사용자 비공개 캡처는 개인 작업용이라 카탈로그와 무관하고, 잘못 열면 "이 URL처럼 만들기"의 뒷문이 된다.
4. **라이선스 데이터셋·오픈소스 중 실제로 쓸 수 있는 것은 5개뿐**(Figma Community 무료 파일 CC BY 4.0 · HTML5 UP CC BY 3.0 · shadcn/ui MIT · Flowbite OSS MIT · WebSight CC BY 4.0 합성). Awwwards·Mobbin·Dribbble/Behance·Framer·Cruip·Flowbite Pro·Tailwind Plus는 약관이 재사용 또는 **"웹빌더/경쟁 템플릿 제작"을 명시적으로 금지**한다. 이 "경쟁 제품 금지" 조항은 흔하므로 큐레이션 절차(계획 0.5)의 체크 항목에 넣어야 한다.
5. ★ **추천 조합(베타 20건, FR-CAT-06)**: internal 14 (자체 생성, 렌더 썸네일) + licensed 6 (에이전시 opt-in 4 + 허용 라이선스 유래 2) + 사용자에게 안 보이는 **근거 코퍼스 100~300건**(경로 3). 이 조합의 전제는 A절의 렌더러(G1)와 썸네일(G9)이다 — **데이터 확보 문제의 절반은 렌더러 문제다.**

### C-1. 카탈로그가 실제로 필요로 하는 데이터 (제품 관점)

| 필드(TRD 4.1) | 어디에 쓰이나 | V1/V2 |
|---|---|---|
| `composition`(PageDoc) | 템플릿 선택·스타일 조합·생성(FR-SEL-01·02) | **V2 필수** — 이것이 없으면 "고르기만 하고 못 만든다" |
| 태그(업종·목적·무드·레이아웃·미디어) | 필터·추천 점수(FR-CAT-01, TRD 6.1) | V2 |
| 팔레트·타이포 요약 | 비교 보드 행(FR-CMP-02) | V2 |
| 점수(접근성·성능, 측정일) | 카드·추천 가중치 | V2 (internal은 우리 게이트로 측정 가능, 외부 사이트는 측정 자체가 요청 행위) |
| 썸네일 | 카드·탐색 | **V1** — 유일하게 "진짜처럼 보이는" 요소. TRD 106행: internal = 렌더러 스크린샷 |
| 출처·권리 메타 | 원장(TR-POL-06) | 운영 |

→ 외부에서 가져올 수 있는 데이터(스크린샷·태그)는 V1만 채우고, 제품이 동작하는 데 필요한 V2(`composition`)는 **어떤 외부 경로로도 오지 않는다** — 반드시 우리 섹션으로 다시 조립해야 한다. 그러므로 모든 경로의 끝은 "큐레이터가 우리 섹션으로 재조립"이고, 경로의 차이는 **썸네일의 진짜 여부와 태그의 근거**뿐이다.

### C-3. 추천 운영 흐름 (주 단위)

```
[근거 층]  큐레이터 관찰(3) ──▶ 조사 원장(태그·추상 메모, 이미지 0)
           + 허용 라이선스 선별(6)·통계(8)   │
                                            ▼
[제작 층]  Designer 변형 명세(근거 ≥3) ──▶ Developer 렌더 변형 ──▶ 유사도·루브릭 게이트
                                            │
                                            ▼
[카탈로그] 큐레이터 조립(4) ──▶ 렌더 썸네일·점수 자동 ──▶ 공개(internal)
           파트너 제출(2) ──▶ 권리 확인 ──▶ 우리 섹션 재조립 ──▶ 제출자 승인 ──▶ 공개(licensed, 원본 썸네일)
[사용자]   비공개 참고 캡처(5) — 카탈로그·추천·생성과 격리
```

- **베타 20건 목표(FR-CAT-06)** 달성 경로: internal 14(큐레이터 1명 × 1.5주, 렌더러 이후) + licensed 6(파트너 2~3곳 × 2작품 — 첫 파트너는 영환님 네트워크의 에이전시가 현실적 [추정]).
- **속도의 병목은 데이터가 아니라 렌더러다.** 렌더러(G1)·썸네일(G9)이 없으면 internal 카탈로그는 지금처럼 와이어프레임 카드라 V1이 0이다. → C의 첫 작업 = A의 M2a와 같다.
- 파트너 프로그램의 교환 가치: 카드에 제작사 표시(GDWEB 상세의 "제작사" 관행) + 문의 연결. 단 PRD 7.10 "에이전시 검색·견적 중개 제외"와 부딪히므로 **표시까지만**, 중개는 하지 않는다.

### C-5. 결정 후보

1. ★ **제품 정의 변경: "레퍼런스 = 검증된 조합"** — 카탈로그 카피·PRD 1절·PRD 190행 위험 대응을 이 정의로 고친다. (대안: V1 "남의 사이트 대량 탐색"을 핵심 가치로 유지 — 합법 경로가 없어 실현 불가, 기각.)
2. ★ **베타 카탈로그 = internal 14 + licensed 6 + 근거 코퍼스 100~300(비공개).** 경로 (4)+(2)+(3) 조합. 렌더러(A절 M2a)가 선행 조건.
3. ★ **경로 (2) 파트너 프로그램을 M0 큐레이션 절차(계획 0.5)에 추가**: 권리 확인서(제작사 + 클라이언트 동의) · 재조립 승인 · 카드 제작사 표시(중개 없음) · 회수 절차(FR-CAT-05).

### D-4. 갈리는 것 1건 — React zip 시점: **조건부로 Opus 안(M2b) 수용**

Opus B-2 설계(고정 템플릿 + 킷 소스 복사 + `content.json`만 가변)가 성립하면 "요청마다 빌드"가 필요 없고, 내 M4 근거("빌드 검증 = 워커")는 그 전제 위에 있었으므로 함께 사라진다. 다만 조건 셋을 건다.

1. **"CI"는 지금 저장소에 없다.** [사실] `.github/`·`.gitlab*`·`circle*`·`**/workflows/*.yml`(깊이 3) 모두 0건(`e4b9487`). 황금 프로젝트 빌드를 돌릴 CI 자체가 M2b의 새 인프라 항목이다 — 워커보다 싸지만 0은 아니다.
2. **TDD T-GEN-02 개정이 필요하다.** [사실] `docs/05-tdd/TDD.md:181` "생성 zip을 임시 디렉터리에 풀고 `npm install --offline`·`npm run build` 성공"은 산출물 단위 테스트다. CI 형식으로 바꾸되, **황금 프로젝트는 손으로 만든 템플릿이 아니라 같은 codegen 경로가 만든 zip**이어야 T-GEN-02의 뜻이 남는다. PRD FR-PUB-02(`docs/02-prd/PRD.md:141`) 수용 기준 "zip에서 `npm install && npm run build` 성공"은 요청 단위를 명시하지 않아 CI 판정으로 읽어도 어긋나지 않는다.
3. **성립 PoC를 M2b 초가 아니라 VS-1 마지막 handoff로 당긴다**(반나절 [추정]): 변형 4개 킷 소스 복사 + `content.json` → 로컬 `npm run build`. 이유: 킷 import 가드(Opus B-1 8)와 상호작용 규칙(B-1 9)은 VS-1 킷 4개를 짤 때 이미 지켜져야 하는데, 검증을 M2b로 미루면 26변형을 규칙 위반 상태로 짤 위험이 있다.

부수 사실 하나: 정적 HTML은 미리 컴파일한 `kit.<hash>.css`를, React zip은 사용자 쪽 Tailwind 빌드를 쓰므로 **CSS 바이트는 두 형식이 같지 않다**(같은 소스라 시각은 같다). T-GEN-08(정적 HTML 픽셀 비교 0.1%, `TDD.md:187`)을 React zip 빌드 결과에도 적용해야 "같은 `(r, L, G)`의 파생물"이 검증된다.

→ **결론: PoC 통과 시 React zip = M2b 종료 조건(브라우저 단독, 워커는 M4 스팟 체크), 실패 시 M4.** 이 조건이면 이견 없음.
