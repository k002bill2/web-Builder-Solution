## 0. 결론 (요약)

1. **GDWEB의 분류 체계 자체가 "디자인 선택 언어"다.** 선정작 목록은 부문·등급·연도 외에 **업종(36) · 타겟층(11) · 표현방법(16) · 디자인컨셉(22) · 주색상(13)** 5축으로 필터되고, 상세 페이지는 이 축을 그대로 써서 "유사 디자인컨셉 / 유사 표현방법 / 유사 업종" 추천을 보여준다. 2005년부터 심사위원·에이전시가 써 온 축이므로, 우리 솔루션의 **선택 UX(업종 → 목적 → 무드 → 컬러)** 는 이 5축을 추상화해 그대로 IA의 뼈대로 삼는 것이 가장 검증된 출발점이다.
2. **수집은 "수동 관찰 → 추상 태깅"만 가능하다.** robots.txt가 `User-agent: * / Disallow: /`(검색엔진 4종만 예외)이고, 이용약관 제13조가 콘텐츠의 제3자 무단 사용·인용을 금지한다. 선정작 스크린샷은 원저작자(제작사·클라이언트) 저작물이다. 따라서 패턴 코퍼스는 **이미지를 저장하지 않고 사람이 본 뒤 구조·규칙 수준으로만 기록**하는 방식이어야 하며, 자동 크롤링·스크린샷 저장 기반 분석은 배제한다. (→ Opus 5.5 담당 D와 교차 확인 필요)
3. **MVP는 "섹션 조립형 + 테마 토큰 스왑"이다.** 자유 드래그앤드롭 에디터·커머스·CMS·AI 문구 생성은 MVP 밖. 업종 프리셋 1개를 고르면 5~7개 섹션이 조립되고, 무드·컬러 토큰을 바꾸면 전체가 일괄 변경되며, 텍스트·이미지만 교체해 서브도메인으로 발행하는 흐름까지가 MVP다. 경쟁 5사 중 이 "축 기반 선택 → 토큰 일괄 스왑"을 초보자용 기본 흐름으로 제공하는 곳은 확인되지 않았다(Wix Studio의 Design libraries는 전문가용).
4. **차별점은 '템플릿 수'가 아니라 '고르는 방식'이다.** Wix 2,000+ 템플릿, 카페24 디자인센터 33만+ 상품은 선택 과부하를 만든다. 아임웹은 템플릿 변경 시 기존 디자인이 초기화된다(공식 FAQ). 우리는 "템플릿"을 노출하지 않고 **구조(섹션 세트) × 스타일(토큰 테마)** 를 분리해 조합하도록 한다.

## A. 솔루션 기획 제안

### A-5. 대상 사용자
| 세그먼트 | 상황 | 왜 우리인가 |
|---|---|---|
| **1차: 소상공인·스타트업·기관 실무자** | 에이전시 견적(수백만~수천만 원)은 부담, 아임웹·Wix는 "템플릿 고르고 나면 결국 디자인 감각이 필요"해서 결과가 밋밋함 | "수상작급 구조와 스타일 조합"을 **고르기만 하면** 나온다 |
| 2차: 소규모 에이전시·프리랜서 | 1차 시안을 빨리 만들어 발주자와 방향을 맞추고 싶음 | 축 기반 시안 3종을 몇 분 안에 생성, 이후 자체 개발로 넘김 |
| 3차(후순위): 마케터 | 캠페인·행사 랜딩 | 목적 축 "프로모션/행사" 프리셋 |

### A-6. 핵심 가치 제안
1. **선택이 곧 디자인이다.** 업종·목적·무드·컬러 4번의 선택으로 완성도 있는 첫 화면이 나온다. 템플릿 목록을 스크롤하지 않는다.
2. **구조와 스타일이 분리된다.** 섹션 구성을 바꿔도 스타일이 유지되고, 무드를 바꿔도 콘텐츠가 유지된다(아임웹의 "템플릿 변경 = 초기화"와 정반대).
3. **패턴은 검증된 것만.** 각 섹션 패턴에는 "어떤 업종·무드에서 반복 관찰됐는가"라는 근거 메타가 붙는다(원본 이미지는 저장하지 않음).

### A-7. 서비스 흐름 (탐색 → 선택 → 편집 → 발행)

```
[탐색]  업종 선택 → 목적 선택 → 무드(컨셉) 2개 이하 → 대표색 1개
          └ 화면: 축 조합에 맞는 "추상 프리뷰"(우리 자체 렌더) 3~6개 카드, GDWEB 원본 이미지 없음
[선택]  프리셋 1개 확정 = 섹션 세트(5~7개) + 테마 토큰(컬러·타이포·간격·모션 강도)
[편집]  섹션 단위 편집: 텍스트·이미지 교체 / 섹션 추가·삭제·순서 / 테마 토큰 스왑 / 모바일 미리보기
[발행]  서브도메인 즉시 발행 → (후속) 커스텀 도메인 연결, 재발행
```

### A-8. MVP 범위 제안

**IN (MVP)**
- 업종 프리셋 8~10종(GDWEB 업종 36종을 발주 빈도 기준으로 묶음: 기업소개 / 쇼핑·브랜드 / 식음료·뷰티 / 건강·의학 / 교육·학원 / 관공서·단체 / IT·소프트웨어 / 프로모션·행사 / 문화·예술·공연 / 건축·부동산)
- 목적 4종(소개형 / 랜딩·프로모션형 / 포트폴리오·갤러리형 / 문의·예약형)
- 무드 6~8종, 대표색 8~12종(토큰 프리셋)
- 섹션 패턴 라이브러리 초기 30~40종(히어로 4~6 · 소개 · 서비스/제품 그리드 · 특징 · 실적/수치 · 갤러리 · 고객사·로고 · 후기 · FAQ · CTA · 문의 폼 · 지도/오시는 길 · 푸터 등)
- 섹션 단위 편집기(텍스트·이미지·순서·표시 여부) + 테마 토큰 스왑 + 반응형 자동
- 서브도메인 발행, 기본 SEO 메타, 문의 폼(이메일 전달)

**OUT (MVP 이후)**
- 자유 드래그앤드롭·픽셀 배치, 커스텀 CSS/코드
- 커머스(장바구니·결제), 회원, 예약 결제
- CMS/블로그 컬렉션, 다국어
- AI 문구·이미지 생성(2단계에서 "빈 섹션 초안 채우기"로 한정 도입 검토)
- 커스텀 도메인은 MVP+1

## D. PRD / TRD 요구사항 후보

**PRD (기능·UX)**
1. 선택 축은 업종 / 목적 / 무드(컨셉) / 대표색 4개로 고정하고, 각 축의 값은 GDWEB 5축을 추상화한 자체 어휘로 정의한다(GDWEB 라벨을 그대로 쓰지 않는다).
2. 업종 프리셋 8~10종 × 목적 4종의 조합마다 기본 섹션 세트(5~7개)를 사전 정의한다.
3. 탐색 화면은 GDWEB 원본 이미지를 쓰지 않고, 자체 렌더한 추상 프리뷰 카드만 노출한다.
4. 프리셋 상세는 "같은 무드 / 같은 업종 / 같은 표현방법의 다른 프리셋"을 추천한다(GDWEB 상세의 유사작 추천 구조 차용).
5. 편집기는 섹션 단위(텍스트·이미지 교체, 추가·삭제·순서, 표시 토글)로 제한하고 픽셀 배치는 제공하지 않는다.
6. 테마 토큰(컬러·타이포·간격·모션 강도) 스왑은 콘텐츠를 보존한 채 전체 페이지에 즉시 반영된다.
7. 반응형은 자동 처리하고 사용자는 모바일 미리보기만 확인한다(식스샵 방식).
8. 발행은 서브도메인 즉시 발행, 커스텀 도메인은 MVP+1.
9. 축 조합·프리셋 상태는 URL로 공유·복귀 가능해야 한다.
10. 로그인 전 스크랩(찜)은 로컬에 저장하고 가입 시 동기화한다.
11. 사용자가 고른 축 조합·최종 프리셋·스왑 이력을 이벤트로 기록해 축 어휘를 개선한다.

**TRD (데이터·기술·정책)**
12. 패턴 코퍼스 스키마: `pattern_id, section_type, layout_rule, token_refs, observed_industries[], observed_moods[], evidence_note(텍스트), observed_at` — **원본 URL·스크린샷 필드는 두지 않는다**.
13. 패턴 수집은 사람이 GDWEB을 열람하며 구조·규칙만 기록하는 수동 큐레이션으로 한정하고, 자동 크롤러·스크린샷 저장 파이프라인은 만들지 않는다(robots.txt·약관 제13조).
14. 디자인 토큰은 W3C Design Tokens 형식(JSON) 등 표준 포맷으로 관리해 테마 스왑을 데이터 교체로 구현한다(포맷 확정은 Opus 담당 C/D와 합의).
15. 섹션 컴포넌트는 "구조(슬롯) + 토큰 바인딩"으로 정의하고, 프리셋은 섹션 ID 배열 + 테마 ID의 참조로만 구성한다.
16. 발행물은 정적 HTML/CSS/JS로 빌드해 CDN에 배포한다(초기 호스팅 비용·보안 면적 최소화).
17. 문의 폼은 서버리스 엔드포인트 + 이메일 전달, 스팸 방지(rate limit·honeypot) 포함.
18. 코퍼스 항목마다 "GDWEB 특정 선정작과 1:1 대응되지 않음"을 리뷰어가 확인하는 체크 단계를 둔다(복제 방지 게이트).

## E. Opus 5.5 산출물(`claude-opus-5.5.md`, 2026-09-25 03:02)과의 교차 확인

**일치 (조정 불필요)**

- 편집기: 섹션 단위, 픽셀 자유 배치·임의 CSS는 MVP 제외. 발행은 정적 빌드 + CDN.
- "탐색" 대상(Opus 쟁점 1): 이 문서 A-7의 탐색 대상도 **우리 프리셋 갤러리**이지 GDWEB 갤러리가 아니다. GDWEB 데이터 활용 전제는 없다(Opus 쟁점 2 해소).
- 심사 기준: Opus가 `/sub/process.asp`에서 확보(비주얼디자인·정보구성·기술요소·웹아이덴티티). 이 문서 A-4의 "확인 필요"는 그 절로 대체한다.

**조정 제안 (스레드에서 1회 정리)**
1. **목적 축 개수**: 이 문서 4종 vs Opus 6종. → Opus 6종을 채택하되, 프리셋은 업종 × 목적 전조합(최대 60)이 아니라 **업종별 대표 목적 2~3개만 사전 정의**하고 나머지는 섹션 세트 규칙으로 파생한다.
2. **업종 10종 목록 통합안**: 병·의원 / 법률·세무·전문직 / 교육·학원 / 음식·카페·식품 / 뷰티·살롱 / 건축·인테리어·부동산 / 제조·B2B 기업소개 / IT·스타트업 / 공공·단체·협회 / 문화·예술·행사·프로모션. (Opus 안의 "포트폴리오·개인"은 업종이 아니라 목적 축으로 이동)
3. **LLM 스키마 채우기**: Opus는 MVP 보조, 이 문서는 MVP 밖. → **수용하되 범위를 "빈 슬롯의 카피 초안"으로 한정**한다. 변형 후보 순위는 규칙 기반으로만 결정하고, LLM 실패·타임아웃 시 정적 플레이스홀더로 폴백한다.
4. **표현방법 축의 위치**: GDWEB "표현방법"(사진/영상/3D/일러스트/타이포)을 사용자 선택 축에 넣지 않고 **히어로 섹션 변형의 미디어 슬롯 속성**으로 둔다. Opus C-1 섹션 변형 체계와 맞는지 확인 요청.
5. **섹션 수량**: Opus 16유형 × 2~4변형(32~64)과 이 문서 30~40종은 같은 범위다. Opus 표기를 정본으로 한다.

## F. AI 의존도·구축 방식 판단 (2026-09-26, 요청자 질문에 대한 회신 — PRD 입력용)

질문: "LLM에게 홈페이지를 만들게 하는 편이 낫지 않은가 / 이 기획은 AI 없이 자체 제작이 가능한가"

**결론**
1. **런타임은 AI 없이 완주하도록 설계됨.** 프리셋 → 섹션 세트 → 토큰 스왑 → 정적 발행이 전부 규칙 기반. LLM은 빈 슬롯 카피 초안용 선택 플래그. 근거: `claude-opus-5.5.md` D-3 표(① 규칙 기반 = MVP 핵심, ③ LLM 자유 코드 생성 = 제외), `gpt-sol.md` 192행, 본 문서 A-8 OUT 항목.
2. **"프롬프트 → 홈페이지" 제품으로 선회하면 카페24·Wix·Framer와 정면 경쟁.** [사실] 카페24 AI 홈페이지 빌더(`https://homebuilder.cafe24.com/`)가 업종 선택 → 전체 구성 → 대화 수정을 이미 제공. [추정] 소규모 팀에는 모델 비용·품질 편차·특정 사이트 모사 통제 불가가 동시에 작용하며, "선정작 복제 금지" 원칙을 기술적으로 보장할 수 없음.
3. **규칙 기반 라이브러리는 초기 비용↑ 한계 비용≈0.** LLM을 나중에 얹을 때 스키마가 안전장치가 됨. 순서는 규칙 먼저, LLM은 그 위에.
4. **솔루션 개발 자체를 LLM 코딩 에이전트로 하는 것은 적합.** 섹션 계약(JSON 스키마)·DTCG 토큰·Puck·정적 빌드 구조라 "변형 1개 = 스키마 + lint + 스냅샷 통과"의 독립 작업으로 분해됨. 에이전트가 못 하는 것: 무드별 디자인 품질 판단(사람 디자이너 리뷰), GDWEB 수동 큐레이션(정책상 사람), 법무 검토.
5. **병목은 AI 유무가 아니라 디자인 자산 수량.** 16유형×2~4변형×8무드×10업종은 코드보다 자산 제작이 오래 걸림. 첫 목표는 GPT-Sol 베타 절단(12유형×2변형, 5업종×3목적×4무드).

**PRD 요구사항 후보 추가**
19. 조립·미리보기·발행의 핵심 경로는 LLM 호출 없이 완주해야 한다(LLM 장애·비용·허위 문구가 발행을 막지 않음). GPT-Sol 결정안과 동일.
20. 개발 파이프라인: 섹션 변형마다 스키마 검증 + lint + 시각 스냅샷 게이트를 두고, 에이전트 제작분은 사람 디자이너 승인 후 라이브러리에 편입한다.
