## 결함

### D1 (P3) — 메모리 저장에서 "저장 중…" 단계가 그려지지 않는다
- 재현: 편집기(1280) → Hero 제목 입력 → 입력 멈춤 → 저장 상태 글자를 MutationObserver(`characterDataOldValue`)로 기록.
- 기대 (SPEC 3.2 E-S06): "저장 상태 글자 '저장 전 변경 있음' → '저장 중…' → '이 탭에 저장됨 · 12초 전'" · E-AC-08 "저장 상태 전이 '저장 전 변경 있음 → 저장 중… → 이 탭에 저장됨 · N초 전'(메모리)".
- 실제: 2006ms에 "저장 전 변경 있음" → "이 탭에 저장됨 · 방금" 한 번만 바뀜. `useAutosaveScheduler.ts:184`는 `saving`을 내보내지만, 메모리 저장소가 같은 task 안(마이크로태스크)에 끝나 React가 `saving`과 `saved`를 한 번에 묶어 그린다(추정, L2 — 코드 읽기 + DOM 기록).
- 영향: 사용자에게 손실 없음(저장은 즉시 끝남). 서버 구현(네트워크 지연)에서는 보일 가능성이 높다. SPEC 문장과 화면이 다른 점만 기록.
- 필요한 결정: SPEC을 "메모리 구현은 '저장 중…'이 순간이라 보이지 않을 수 있다"로 완화할지, 최소 표시 시간을 둘지. 캡처 `shots/1280/e7-saved.png`.

## 한계
- STALE_DOC 충돌: 브라우저 재현 불가(위 E7 관찰).
- 1024 `select` 키보드 팝업을 연 채 viewport를 768로 바꾸면 탭 배치로 바뀌지 않았다(3차 실행 마지막 관찰 `tablist=false, select=true`; 2차 실행에서 이 순서 때문에 768 E4가 실패). 네이티브 팝업이 열린 상태에서 CDP로 창 폭을 바꾼 **하네스 조건**이라 결함으로 올리지 않고, 해당 관찰을 흐름 맨 끝으로 옮겨 E4는 영향 없이 다시 실행했다. 실제 사용자는 팝업을 연 채 창 폭을 바꾸기 어렵다. 필요하면 실기기 회전으로 확인.
- 1·2차 실행 수정 내역(스크립트만): 페이지 안 긴 `setTimeout` 루프가 30초 시간 제한을 넘김 → 관찰기만 페이지에 두고 대기는 Node에서 · Tab 샘플이 문서 끝(브라우저 UI)을 body로 셈 → 문서 끝으로 구분 · 폭 변경 뒤 배치 전환 대기 추가.
- 1초 전환 측정 = 클릭 → 프레임 인라인 스타일 반영까지(rAF). 페인트 완료 시각은 아니다.
- 도구: 전역 규칙은 브라우저 검증을 ego-browser/aside로 한정하지만, 브리프가 "같은 도구, 새 의존성 금지"로 선례의 agent-browser를 지정해 그대로 썼다(설치 없음).
