# PERSIST-E0 — P1-E0 진입 몫 번들 실측 (ADR-007 MQ-P5 관문)

## 판정

**128.58KB 이하 배치안 없음 → ADR-007 P5 ★A대로 P1 멈춤, 예산 MQ 재상신 자료.**

- 측정한 4안 중 최저 = **안1-min 129.00KB**(첫 실행 연결 정리 포함, `7ba07b1`) → 판정선 128.58 대비 **+0.42KB 초과**(잡음 ±0.02 포함 +0.42~0.46). 검사기는 라우트 한도 129에도 실패로 판정한다(129.00 > 129 — 반올림 전 값).
- 측정 범위는 ADR-007 5절 P1-E0 진입 몫 전부다: IDB 열기, StudioState 1건·진입 문서 1건 읽기, 봉투 확인, 대기 Promise, `"local"` 분기, 문서 하이드레이션 직후 이미지 자동 복원 시작(부록 Codex 제약 2).
- 근거 L1: 4안 모두 `npm run build`의 check-bundle-size 출력이다. 수동 보정이 들어간 값은 표에 따로 표시했다.

## MQ 재상신 자료 (Jarvis → 영환님)

- 최소 초과량: **+0.42KB**(안1-min 129.00 vs 판정선 128.58, 잡음 포함 +0.42~0.46). 라우트 한도 129와는 같거나 0.01 위다(검사기 실패).
- 선택지(이 레인은 결정하지 않음):
  1. 판정선을 129.10 안팎으로 올리기. 다만 개정 5 한도 129를 넘으므로 한도 개정도 함께 필요하다.
  2. 구조 점검으로 /studio 진입의 다른 몫을 0.45KB 이상 덜어 낸 뒤 진행하기. 후보 = StudioLayout 18.67KB 안의 진입 시 불필요한 분기(점검 필요, 이 레인 범위 밖).
  3. 이미지 자동 복원을 진입이 아니라 첫 렌더 뒤 idle 등으로 미루기. 그래도 검사기 분류 규칙상 "조작 없이 실행"이면 자동이므로 바이트는 같다 — **효과 없음**[L1 검사기 주석 규칙].
- 하한 +0.50의 구성: IDB 원시 API 래퍼(Promise화)와 대기 연결이 대부분이다. 이 비용은 영속을 하는 한 피할 수 없다.

## 스파이크 범위 밖 · 단순화 (실제 P1a에서 달라질 수 있음)

- 쓰기 큐·이행·스냅샷·삭제·다중 탭 없음. 그래서 실제 IDB 데이터를 만드는 경로가 없고, 브라우저 실측(Ego Lite)은 하지 않았다(REPORT 사유).
- 하이드레이트한 StudioState에 deepFreeze를 다시 걸지 않았다. 진입 문서 머리는 `/studio/:id` 1건만 읽으므로 `/projects`의 hasDoc는 그 1건만 맞다. 목록 전체 hasDoc는 P1a에서 문서 머리 요약을 StudioState 레코드에 함께 두는 안을 권한다(같은 1건 읽기 → 진입 몫 추가 0 예상[추정]).
- `ProjectPersistence` 타입에는 `"local"`을 더하지 않았다(계약 범위 판단 보류). 값은 `as string as` 캐스트로, 문구는 남는 분기로 넣었다. 타입만 바꾸는 것은 바이트 0이다.
- StudioPanels·ExportAfter의 "이 탭에 저장돼 있습니다" 안내 문구 분기는 넣지 않았다. ExportAfter는 조작 뒤 청크다. StudioPanels 캡션 분기는 P1c 문구 레인 몫이며 +0.01 수준으로 추정한다.

## ② 진행 중 3안 생성 잡 복원 — "재계산 재시작" vs "hidden 영속" (구현 0, L1)

### 사실 (코드)
- 잡 계산은 요청 순간 세 안을 한 번에 끝낸다. 결과는 `StoredJob.hidden`에 숨겨 두고, `getJob`이 조회마다 한 안씩 공개한다(`memoryGenerationRepository.ts` getJob · `studioStore.ts` StoredJob 주석). 즉 "진행 중"은 계산 중이 아니라 **공개 대기 상태**다.
- `job`만 복원하면 `getJob`의 `next = findIndex(pending && hidden[i])`가 −1이 된다. 그러면 running 그대로 반환되어 **영원히 끝나지 않는다**. `retryFailed`도 `retryJob`이 `!isTerminal` → "아직 만드는 중입니다"로 거부한다(`memoryGenerate.ts` retryJob). 따라서 Codex 제약 1 지적은 사실이다.
- 결정성: `internalCompose.ts:3` "순수·결정적: 시각·Math.random 0, seed = hash(업종|순번|시도|버전)"이고, `composeFor`의 입력은 저장된 버전(base+adjustments)·library·GENERATOR_VERSION뿐이다. → 같은 버전·같은 생성기면 재계산 결과가 바이트 단위로 같다. 단, `outcome` 실패 주입(테스트 전용)과 `attempts`는 재계산으로 재현되지 않는다(제품 경로에는 주입 없음).
- 멱등 키 = (profileId, version, library_version, generatorVersion)이다. 생성기 버전이 바뀌면 `findJob`이 옛 잡을 찾지 않는다(새 키). 따라서 hidden을 영속해도 **낡은 결과가 새 생성기 이름으로 노출되지 않는다**. 옛 잡 레코드는 쓰레기로 남는다.

### 비교

| 기준 | A. 재계산 재시작 (복원 시 hidden 없는 미완료 잡 → `composeFor` 재실행) | B. hidden 영속 (StoredJob 통째로 저장) |
|---|---|---|
| 결정성 근거 | 순수·결정적이라 같은 결과 [L1 internalCompose:3] | 계산 결과 자체를 보관하므로 근거가 필요 없다 |
| 수정 지점 | 하이드레이션 뒤 미완료 잡 탐지 + `memoryGenerate.composeFor` 호출(신규 복원 함수) · `attempts` 재설정 규칙 | `studio` 레코드 직렬화에 hidden·attempts 포함(ADR 3절 "job만, hidden·attempts 제외" 한 줄 개정)뿐. getJob·retryFailed 변경 0 |
| **진입 영향** | `/profile (3안 있음)`에서 복원 즉시 재계산하면 memoryGenerate(조작 뒤)가 자동이 된다 → **121.59 → 127.08 (+5.49, 125 초과 ✗)**[L1 closure 계산 `/tmp/e0-closure.mjs` 기준선 dist]. 안1 위에서는 127.54 | **+0** — hidden은 이미 읽는 StudioState 레코드 안의 데이터일 뿐 코드가 아니다 |
| A의 조작 뒤 변형 | 미완료 잡을 "실패·재시도 가능"으로 바꿔 복원 → 사용자가 "다시 시도"를 누르면 retryJob(조작 뒤). 진입 +0이지만 실패 문구가 거짓(INFRA "생성 서버에 연결하지 못했습니다")이 되어 새 코드·문구가 필요하고 클릭 1회가 는다 | — |
| 저장 크기 | 0 | 안 3개의 ComposedResult(구조안 JSON) — 수 KB/잡 [추정] |
| 형식 부채 | 없음 | ComposedResult 모양이 저장 형식이 된다 → 봉투 schemaVersion 이행 대상. 해결: 버전 불일치 시 미완료 잡의 hidden을 버리고 A-변형(재시도)으로 내린다 |
| 서버 이행 | 서버는 잡 상태를 서버가 가진다 → 둘 다 메모리 구현 한정 | 동일 |

### 추천 ★ B. hidden 영속 (+ 봉투 버전 불일치 시에만 "다시 시도" 강등)

이유:
1. 진입 비용이 0이다. A는 /profile(3안 있음)을 125 밖으로 민다.
2. getJob·retryFailed를 바꾸지 않는다. 지금 "진행 중"은 공개 대기일 뿐이라 영속한 hidden이 있으면 새로고침 뒤 폴링이 그대로 끝까지 간다.
3. 낡은 결과 노출은 멱등 키의 generatorVersion이 막는다.

필요한 후속(P1a BRIEF 입력):
- ADR 3절 `studio` 행 "생성 잡은 `job`만, `hidden`·`attempts` 제외"를 "StoredJob 통째로"로 고치는 문서 개정(Jarvis).
- "새로고침 중 생성" 테스트 = 요청 → getJob 1회 → store 직렬화/역직렬화 → getJob 반복으로 succeeded 도달.
- 이행 실패 시 강등 문구는 Designer 몫이다.
