## MQ-S1 — 프로필 화면이 "문서 있음"을 언제 아는가 (진입점 모양)

[사실 L1] 프로필 화면 `series.project`는 `{projectId, name}`뿐이다. `hasDoc`·`candidateId`는 `ProjectSummary`(`projectRepository.ts:44-53`)에 있고, 그걸 읽는 `memoryProjectRepository`는 /profile에서 조작 뒤 청크다(`check-bundle-size.mjs:78`). `DOC_EXISTS` 오류는 기존 문서(revision 포함)를 동봉한다(`memoryDocBook.ts:384-385`). /profile 첫 화면 99.87/100.

| 선택 | 내용 | 얻는 것 | 잃는 것 |
|---|---|---|---|
| ★**A** | 버튼은 "X안으로 편집 시작" 그대로. 누른 뒤 `DOC_EXISTS`이고 안이 다르면 대화상자에 EQ-2 A의 두 버튼("편집기 열기 (B안 · v3 편집 중)" / "C안으로 새로 시작") | 진입 바이트 0 · 저장소 계약 변경 0 · 대화상자가 곧 확인 단계 | EQ-2 A "진입 때부터 주 버튼 이름이 바뀜"과 다름(SPEC RS-D1) · 한 번 더 클릭 |
| B | 진입 뒤(마운트) `listProjects`/`getDoc`으로 문서를 읽어 EQ-2 A 원문 그대로 버튼 2개 | EQ-2 A 원문 일치 · 누르기 전에 상태가 보임 | `memoryProjectRepository`가 /profile **진입 직후**로 올라옴 — **예산 증액 필요 가능성 높음**(추정 L3) · 진입 때 읽은 revision이 낡을 수 있어 누를 때 다시 읽어야 함 |
| C | A + 캡션에 "편집 중: B안 · v3"을 누른 뒤부터 계속 표시 | A의 예산 + 상태 가시성 일부 | 처음 누르기 전에는 여전히 모름 · 문구 증분 |

근거: 여유 0.13 KB에서 저장소 청크를 진입에 올릴 수 없다 — 같은 정보가 `DOC_EXISTS`에 이미 온다.

## MQ-S2 — 다른 탭이 쓰기 잠금을 가질 때 새로 시작

[사실 L1] 지금 `startDoc`은 메모리 `commit()` 뒤에 IDB flush가 INFRA로 실패한다(`memoryProjectRepository.ts:65-66` · `localSync.ts:187-190`). 잠금 없는 탭에서 restart하면 탭 메모리 = 새 문서, IDB = 옛 문서·스냅샷 없음 — 새로고침하면 사라지는 "새로 시작"과 "실패했다"는 문장이 동시에 생긴다. 지우기 흐름은 잠금을 먼저 잡는다(P1D-SPEC 70행).

| 선택 | 내용 | 얻는 것 | 잃는 것 |
|---|---|---|---|
| ★**A** | restart만 `docs.start` **전에** 잠금 확인(`gate.enter()`), `writer`가 아니면 INFRA로 던져 쓰기 0 · 문장 R-E2 | 메모리·IDB 갈라짐 0 · 거짓 상태 0 · 지우기와 같은 패턴 | **저장소 내부 순서 변경**(인터페이스·스키마 불변) · `LocalSync`에 `enter` 노출 · `/studio` 진입 직후 청크(memoryProjectRepository) 몇 줄 증가 — 실측 필요 |
| B | 계약 그대로 · INFRA 사유를 그대로 보여 주고 이동 0 | 코드·예산 변경 최소 | 갈라짐 남음 · 문장이 "탭 안에서는 바뀌었지만 저장되지 않았습니다"까지 말해야 정직 |
| C | A를 create·restart 모두에 | create의 같은 갈라짐도 닫힘 | 범위 확장(B-ER-01 밖) — 별건 BACKLOG 권장 |

근거: restart는 사용자의 편집 문서를 바꾸는 유일한 프로필 쪽 쓰기라 "실패 = 변화 0"이 지켜져야 한다.

## MQ-S3 — 대화상자에 두 버전의 대비 결과를 보여 줄까 (B-ER-01 "대비 통과 버전으로 옮기기")

[사실 L1] 게이트 대비 줄은 문서 `profileVersion`으로 정해진다(`engine/gate/contrastRow.ts:29-40`). 프로필 화면은 이미 대비 검사를 그린다(`components/profile/PaletteContrast.tsx:59-62`).

| 선택 | 내용 | 얻는 것 | 잃는 것 |
|---|---|---|---|
| ★**A** | 두 버전 결과가 **다를 때만** 한 줄 R-D5("지금 v3 미달 2 · 새 v4 모두 통과" / 새 버전도 미달이면 경고 문형) | 옮기는 이유·효과가 결정 지점에 보임 · 조작 뒤 청크라 예산 0 | 대화상자 코드 증가(조작 뒤) · 대비 집계 함수 재사용 확인 필요 |
| B | 표시 없음 | 단순 | 사용자가 새 버전이 통과하는지 모른 채 내용을 버릴 수 있음 |
| C | 늘 표시(같아도) | 일관 | 같은 결과면 소음 |

## MQ-S4 — "새로 시작 전" 스냅샷 이름에 시각을 붙일까

[사실 L1] 저장소 이름은 고정 "새로 시작 전"(`memoryDocBook.ts:396`), "복원 전"은 `timedName`으로 "복원 전 · HH:MM"(`:311`). 목록 캡션에는 시각이 있다(`SnapshotDialog.tsx:231`).

| 선택 | 내용 | 얻는 것 | 잃는 것 |
|---|---|---|---|
| ★**A** | 그대로(고정 이름) — 이 레인 범위 밖 | 저장소 변경 0 · 기존 테스트 불변 | 반복 새로 시작 시 같은 이름 여러 개(캡션 시각으로 구분) |
| B | `timedName("새로 시작 전", …)`로 통일 | 복원 전과 일관 · 이름만으로 구분 | **저장소 문자열 변경**(조작 뒤 청크) · 기존 단언 수정 · 성공 문장 R-N1도 시각 포함으로 |

근거: 구분 수단(캡션 시각)이 이미 있고, B는 다른 Developer 레인과 파일이 겹친다.

## MQ-S5 — 편집기 이탈 저장 미보장 (Codex r1 P1, 새로 시작이 드러내는 기존 결함)

[사실 L1] 편집기 이탈 저장은 완료를 기다리지 않고 `retry()`만 부른다(`StudioLayout.tsx:127-134`). 저장 중 추가 편집은 이탈(unmount) 때 버려질 수 있다(`useAutosaveScheduler.ts:100-102,274-278`). 그 뒤 새로 시작하면 "새로 시작 전" 스냅샷에는 마지막 화면 편집이 없다 — revision은 정상이라 `STALE_DOC`로도 못 잡는다.

| 선택 | 내용 | 얻는 것 | 잃는 것 |
|---|---|---|---|
| ★**A** | 이 레인은 문구로만 밝힘(R-D2 "이 저장 기준으로 스냅샷에 남습니다") + 기록 테스트 RS-AC-08c · 이탈 손실 수정은 **별건 BACKLOG**(Jarvis 등록: 이탈 전 `flushed()` 확인, 실패 시 이동 보류) | 범위 유지 · 편집기 파일과 겹치지 않음 | 수정 전까지 드문 손실 경로 남음 |
| B | B-ER-01 구현 레인에 이탈 저장 대기까지 포함 | 한 번에 닫힘 | `/studio` 진입 청크(StudioLayout) 변경 → **/studio 예산 영향** · 범위 확장 |


## MQ-S6 — 쓰기 전 실패(R-E3)와 커밋 뒤 미확인(R-E4)을 어떻게 가르나 (Codex SPEC r1 재검증 P1)

[사실 L1] `call()`은 요청 단계(커밋 전)와 응답 단계(커밋 뒤)에 같은 오류를 던질 수 있다(`memoryProjectRepository.ts:69-83`). flush INFRA(커밋 뒤, `:65-66`)와 잠금 거부 INFRA(커밋 전 — `impl:memoryProjectRepository.ts:121-122`)는 둘 다 `code: "INFRA"`, 사유는 메시지에만 있다(`persistence/infra.ts:1-2`). `ProjectRepositoryError`에 단계·커밋 필드가 없다(`projectRepository.ts:168-192`). Codex 재현: 같은 `Error`를 요청·응답 단계에 넣으면 화면이 받는 모양은 같고 결과는 B안·스냅샷 0 vs C안·스냅샷 1.

| 선택 | 내용 | 얻는 것 | 잃는 것 |
|---|---|---|---|
| ★**A** | **실패 뒤 문서 확인 절차**(SPEC 3.3.1): `UNKNOWN_VARIANT`·`STALE_DOC` 말고는 `getDoc`으로 이 탭 저장소 문서를 읽어 "revision = 이전+1 · 안·버전 = 요청값"이면 R-E4, 아니면 사유(R-E2·R-E2b·R-E3), `getDoc`도 실패하면 결과를 단정하지 않는 R-E5 | 저장소 인터페이스·오류 타입·스키마 변경 **0** · 서버 저장소로 바뀌어도 같은 모양("응답을 잃으면 읽어서 확인") · 다시 시도는 어느 경우든 멱등이라 R-E5도 안전 | 실패 때 읽기 1회(메모리 — 조작 뒤 청크) · 사유 판정이 메시지 끝 문자열에 기댐(RS-R8) · 문장 1개(R-E5) 추가 |
| B | **오류에 단계 정보 추가**: `ProjectRepositoryError`에 `committed?: boolean`, `call()`·`kept()`가 커밋 뒤 실패에 표시 | 읽기 0 · 판정이 단순 | **저장소 계약 변경**(오류 타입·`call` 래퍼 — `/studio` 진입 청크 `memoryProjectRepository` 증가, 개정 15 restart 몫 +0.05를 잠금과 나눠 씀) · 응답 유실(네트워크)처럼 클라이언트가 커밋 여부를 모르는 경우는 여전히 확인 필요 → A가 결국 필요 |
| C | 가르지 않음: 그 밖 실패는 모두 R-E5 한 문장("확인하지 못했습니다 — 다시 시도") | 코드 최소 | 쓰기 0이 확실한 잠금 거부(R-E2)도 모호한 문장 · "다른 탭을 닫으세요" 같은 행동 안내를 잃음 |

근거: B-ER-01의 원칙은 "실패 = 변화 0이거나, 아니면 그 사실을 말한다"이다. A는 계약을 바꾸지 않고 그 원칙을 지키며, B를 골라도 응답 유실 확인 절차(A)는 남는다.

## MQ-S7 — `/profile` 진입 직후 예산: RS-AC-13 "±0.03"을 지킬까 (구현 실측 +0.36)
